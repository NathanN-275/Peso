## Source facts

- CISA defines `fixed` as identified products containing fixes; `not_affected` means the vulnerability does not affect them and no remediation or mitigation is required. `affected` requires an action statement, which should describe remediation or mitigation. Unresolved status can be `under_investigation`. A `not_affected` statement needs a justification or explanatory impact statement. Product identifiers define applicability; a vulnerable subcomponent can coexist with a `not_affected` enclosing product. [CISA Minimum Requirements, §§2.5–2.7](https://www.cisa.gov/sites/default/files/2023-04/minimum-requirements-for-vex-508c.pdf).
- OpenVEX supports product identifiers, hashes, and nested subcomponents; statements describe a vulnerability's impact on identified products at a point in time. Its example explicitly considers product patching before an upstream component patch. `status_notes` can record the basis of a determination. [OpenVEX v0.2.0, Product Data Structure, Statement Fields, Sample Scenario](https://github.com/openvex/spec/blob/main/OPENVEX-SPEC.md).
- `inline_mitigations_already_exist` requires built-in protection that attackers cannot subvert, users cannot configure or disable, and that completely prevents known attack vectors. CISA warns that effectiveness depends on the threat model and does not automatically transfer between products/services. [CISA Status Justifications, §3.7](https://www.cisa.gov/sites/default/files/publications/VEX_Status_Justification_Jun22.pdf).

## Application and recommendations — inference, not source certification

| Claim | Defensible scope and evidence limit |
| --- | --- |
| `fixed` | Can describe a specifically identified local artifact when evidence establishes that the complete vulnerability fix is incorporated. An unchanged registry version does not preclude this artifact claim. A patch file or successful installation alone is insufficient. The claim cannot extend to an unpatched registry tarball or prebuilt bundle. This follows the product-specific definition above. |
| `not_affected` | Can describe an artifact with a demonstrated qualifying non-exploitability reason. Backport presence alone is not that reason. Use `vulnerable_code_not_present` only for actual absence, `vulnerable_code_not_in_execute_path` only for demonstrated non-execution, and `inline_mitigations_already_exist` only when its strict conditions hold. `component_not_present` cannot describe a component still included. [OpenVEX Status Justifications](https://github.com/openvex/spec/blob/main/OPENVEX-SPEC.md#status-justifications). |
| `affected` + `action_statement` | Appropriate for known affected unpatched artifacts or incomplete mitigation requiring action. Describe the remaining exposure, backport coverage limits, and required replacement/rebuild/verification. An action statement documents work needed; it does not turn the artifact into `fixed`. If actual impact is unresolved, use `under_investigation` rather than inventing certainty. [CISA §2.7](https://www.cisa.gov/sites/default/files/2023-04/minimum-requirements-for-vex-508c.pdf). |

Recommend separate records for the patched build and unpatched Forge bundles. Bind each claim to an artifact digest/build identity and exact vulnerability identifier; preserve patch provenance, incorporation evidence, focused regression results, and analysis of remaining copies and bypasses. An unchanged package/version identifier alone cannot distinguish different bytes. Confirm how the eventual consumer matches these identifiers before using VEX in policy. [OpenVEX Product Data Structure](https://github.com/openvex/spec/blob/main/OPENVEX-SPEC.md#product-data-structure).

Tests support only their exercised cases. A verified source backport does not establish that prebuilt bundles or deployed releases contain it. Retaining an unpatched bundle does not by itself prove exploitability either: assess that artifact separately against the justification criteria and threat model. Document excluded artifacts explicitly; do not convert this note into blanket suppression or a release approval. [CISA Status Justifications](https://www.cisa.gov/sites/default/files/publications/VEX_Status_Justification_Jun22.pdf).
