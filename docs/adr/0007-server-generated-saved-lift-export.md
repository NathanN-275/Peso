# ADR 0007: Generate multi-lift Saved Lift exports on the backend

## Status

Accepted

## Decision

Multi-lift Saved Lift Exports are generated by the backend and delivered through
a temporary authenticated download. This avoids loading several large analyzed
videos into browser memory and makes one ZIP more reliable than coordinating
many client-side downloads. Export preparation runs as a background job so
navigation does not cancel large bundles. The backend enforces lift ownership,
includes each selected lift once as its standard analyzed video, and expires the
generated archive.

The job record is owner-scoped and moves through `queued`, `processing`,
`completed`, `failed`, or `expired`. The browser polls that record and receives a
short-lived signed URL only for a completed, unexpired archive. Duplicate lift
IDs are removed before the job is created, and every selected lift is
revalidated before preparation starts.

Generated ZIPs live in a private, backend-only storage bucket. The default
bundle cap is 50 MB so a Free Supabase project fails predictably at its global
object limit; deployments with a higher Storage limit may raise
`MAX_SAVED_LIFT_EXPORT_BYTES`.

## Context

Saved Lifts can contain videos large enough that downloading and zipping several
of them in a browser is memory-intensive and sensitive to navigation. A server
job also provides one owner-checked status to recover after leaving and returning
to the Saved Lifts page.

## Consequences

- Demo Analysis remains local and cannot create an export job.
- Completed archives remain available for `EXPORT_CACHE_TTL_HOURS`; each signed
  URL is shorter-lived and can be refreshed through authenticated polling.
- Archive cleanup and account deletion remove generated ZIPs from the private
  export bucket.
- The current FastAPI background-task adapter survives browser navigation but
  not an API process restart. Restart-resilient consumption should share the
  durable worker approach described by ADR 0006 when that worker is introduced.
